## Platform Overview

**Purpose:**  
Enterprise cloud migration assessment platform for analyzing IT infrastructure, generating migration reports, and orchestrating AI-driven workflows.  
**Architecture:**  
Microservices-based, with strict separation of concerns, multi-database support, and event-driven communication.

---

### 1. Core Services

- **Frontend:**  
  - React/TypeScript (Mantine UI), port 3000  
  - Central dashboard for project management, document generation, health/status, and graph visualization  
  - API calls routed via backend gateway for consistency

- **Backend Gateway:**  
  - FastAPI, port 8000  
  - Orchestrates requests to all microservices (project, reporting, document, vector, graph, LLM, AI agent, storage, websocket)  
  - Implements ServiceClient abstraction for HTTP calls  
  - Handles authentication, correlation IDs, and error normalization

- **Project Service:**  
  - FastAPI, port 8002  
  - Manages projects, templates, deliverables, and user data  
  - PostgreSQL database (projectdb/projectuser/projectpass)

- **Reporting Service:**  
  - FastAPI, port 8003  
  - Converts markdown to PDF/DOCX using MinIO object storage  
  - Handles document generation and artifact caching

- **Document Service:**  
  - FastAPI, port 8004  
  - Handles file uploads, document parsing, and metadata extraction

- **Vector Service:**  
  - FastAPI, port 8005  
  - Manages ChromaDB vector embeddings for semantic search and RAG

- **Graph Service:**  
  - FastAPI, port 8006  
  - Manages IT infrastructure graph in Neo4j  
  - Entity extraction via LLM and regex fallback  
  - Redis cache for graph and entity results

- **LLM Service:**  
  - FastAPI, port 8007  
  - Provides LLM orchestration (OpenAI, Anthropic, Gemini, Ollama)  
  - Configurable per project via PostgreSQL

- **AI Agent Service:**  
  - FastAPI, port 8008  
  - CrewAI orchestration for multi-agent workflows  
  - Streams agent events to WebSocket for real-time feedback

- **WebSocket Service:**  
  - FastAPI, port 8009  
  - Project-scoped event broadcasting for async operations

- **Storage Service:**  
  - FastAPI, port 8010  
  - MinIO object storage for all file artifacts

---

### 2. Data Layer

- **PostgreSQL:**  
  - Projects, users, LLM configs, deliverables, generation requests

- **ChromaDB:**  
  - Vector embeddings per project (all-MiniLM-L6-v2)

- **Neo4j:**  
  - IT infrastructure graph, project isolation via project_id

- **MinIO:**  
  - Object storage for raw uploads, parsed markdown, generated reports, metadata

- **Redis:**  
  - Caching for graph stats, entity extraction, and topology

---

### 3. Key Code Patterns

- **ServiceClient (backend/app/core/service_client.py):**  
  - Centralized async HTTP client for all microservices  
  - Handles authentication, correlation ID, error handling  
  - Methods for each service: upload, process, download, convert, extract, query, etc.

- **Document Processing Pipeline:**  
  - Upload: `/upload/{project_id}` → MinIO  
  - Process: `/api/projects/{project_id}/process-all` → MarkItDown → ChromaDB → Neo4j  
  - Selective: `/api/projects/{project_id}/process-selected`  
  - Status: `/api/projects/{project_id}/uploaded-files`

- **GraphProcessor (graph-service/app/core/graph_processor.py):**  
  - Async Neo4j/Redis setup  
  - Entity extraction: LLM-first, regex fallback, caching  
  - Graph operations: add, get, stats, delete, topology  
  - LLM calls via httpx to LLM Service  
  - Normalizes LLM output to Entity/Relationship models

- **WebSocket Broadcasting:**  
  - Project-scoped channels  
  - Events: CONVERTED_TO_MD, EMBEDDINGS_ADDED, GRAPH_UPDATED  
  - Handles connection errors gracefully

- **LLM Factory Pattern:**  
  - Provider-based config (OpenAI, Anthropic, Gemini, Ollama)  
  - Project-specific settings in PostgreSQL  
  - Lazy loading and fallback

---

### 4. Service Communication

- **Storage Keys (MinIO):**  
  - `projects/{project_id}/uploads/raw/{filename}`  
  - `projects/{project_id}/uploads/parsed/{filename}`  
  - `projects/{project_id}/metadata/{filename}`

- **Database Patterns:**  
  - Project isolation via project_id  
  - ChromaDB: `project_{project_id}` collections  
  - Neo4j: relationships filtered by project_id  
  - Redis: TTL-based caching for stats and entities

---

### 5. Error Handling & Troubleshooting

- **Graceful Failure:**  
  - Always record metadata, even on conversion failure  
  - WebSocket notifications for async ops  
  - Skip expensive ops if conversion fails

- **Common Issues:**  
  - Backend startup slow (ML model loading)  
  - Missing config.local.json (uses env defaults)  
  - NoSuchKey errors on first upload (not fatal)  
  - Neo4j pool reinit (normal)

- **Health Checks:**  
  - `/health` endpoints for all services  
  - `docker-compose ps` for infra status

---

### 6. Development Workflow

- **Startup Sequence:**  
  1. Infrastructure: `docker-compose up -d postgres neo4j weaviate minio`  
  2. Project Service: `python main.py` (port 8002)  
  3. Backend: `python -m app.main` (port 8000, slow start)  
  4. Frontend: `npm start` (port 3000)

- **Build Commands:**  
  - Fast dev: build-images.ps1, start-platform-dev.ps1  
  - Full compose: `docker-compose up -d`

---

### 7. Project-Specific Conventions

- **Entity Extraction:**  
  - LLM-first, regex fallback, cache results  
  - Relationships: HOSTS, CONNECTS_TO, USES, DEPENDS_ON  
  - Node types: Server, Application, Database, Technology, Service

- **Graph API:**  
  - `/api/graphs/projects/{project_id}/graph` (full graph)  
  - `/api/graphs/projects/{project_id}/topology` (infrastructure view)  
  - `/api/graphs/projects/{project_id}/stats` (stats)  
  - `/api/graphs/projects/{project_id}/extract` (entity extraction)  
  - `/api/graphs/projects/{project_id}/graph` (delete)

- **Frontend Integration:**  
  - All API calls routed via backend gateway  
  - Graph visualization expects nodes/edges  
  - Auto-download for generated documents

---

### 8. Security & Auth

- **Service-to-service auth:**  
  - Bearer token via `SERVICE_AUTH_TOKEN` env var  
  - Correlation ID propagation for traceability

---

### 9. Extensibility

- **LLM providers:**  
  - Easily add new providers via config  
  - CrewAI agent orchestration for complex workflows

- **Document templates:**  
  - Global and project-specific templates  
  - On-demand conversion and caching

- Data is always project-scoped; multi-tenancy is enforced at every layer.

This platform is a robust, multi-service cloud migration assessment tool, with strong separation of concerns, multi-database support, and AI-driven document and graph analysis. All services communicate via HTTP, with centralized error handling and event-driven updates. Entity extraction is LLM-first, with regex fallback and caching. ## CrewAI: Crew Orchestration Overview

**Purpose:**  
Crews are orchestrated groups of AI agents, each with a specialized role, collaborating to perform complex migration assessment tasks.  
Crews enable multi-step workflows, delegation, and real-time feedback via WebSocket.

---

### 1. Crew Structure

- **Crew**:  
  - A named group of agents assigned to a workflow.
  - Has a process definition (sequence of tasks, delegation rules, memory settings).

- **Agent**:  
  - An autonomous AI entity with a role (e.g., “Infrastructure Extractor”, “Risk Assessor”).
  - Has a goal, backstory, allowed tools, and delegation permissions.

- **Task**:  
  - A unit of work assigned to an agent (e.g., “Extract entities from document”, “Generate migration plan”).
  - Has expected output and may depend on other tasks.

- **Available Tools**:  
  - APIs or microservices agents can invoke (e.g., LLM, graph, reporting).

---

### 2. Crew Workflow

1. **Crew Definition**:  
   - Crews, agents, and tasks are defined in config (see backend, frontend, and AI Agent Service).
2. **Workflow Initiation**:  
   - A workflow is started via API (e.g., `/api/agents/crews/{crew_id}/workflows`).
3. **Task Assignment**:  
   - Tasks are distributed to agents based on crew process.
4. **Agent Execution**:  
   - Each agent performs its assigned task, possibly delegating subtasks to other agents.
5. **Tool Invocation**:  
   - Agents call tools/services (LLM, graph, reporting) as needed.
6. **Event Streaming**:  
   - Progress and results are streamed to the frontend via WebSocket.
7. **Result Aggregation**:  
   - Crew aggregates outputs, generates final report or migration plan.

---


---

### 4. Key Features

- **Multi-agent collaboration:**  
  - Agents can delegate, share memory, and coordinate.
- **Tool integration:**  
  - Agents invoke microservices for specialized tasks.
- **Configurable workflows:**  
  - Crews, agents, and tasks are defined in config and can be updated.
- **Real-time feedback:**  
  - WebSocket streams agent progress and results to the UI.
- **Extensible:**  
  - New agents, tools, and workflows can be added easily.

---

**Summary:**  
Crews are the backbone of multi-agent orchestration in your platform, enabling complex, collaborative workflows for migration assessment. Each crew is a configurable group of agents, each with a role and tasks, working together and leveraging platform services to deliver results.
