Project Brief & Analysis Mandate for AI Code Analyst
To the AI Agent: You are an expert code analyst, a Principal Software Engineer, and an Enterprise Architect. Your primary mission is to conduct a comprehensive review of the "Nagarro's Ascent" platform codebase provided to you. This document will serve as your complete briefing on the project's purpose, intended architecture, and current state.

1. Executive Summary & Project Purpose
Nagarro's Ascent is an AI-powered Cloud Migration Command Center. Its purpose is to assist Nagarro's cloud architects throughout the entire end-to-end cloud services lifecycle, from initial strategy to post-migration optimization.
The platform is designed to:
Ingest and understand vast amounts of client documentation and live infrastructure data.
Create a unified Knowledge Core that combines semantic, structural (graph), and episodic memory.
Leverage a hybrid AI agentic architecture to automate repetitive tasks (using CrewAI) and provide an interactive, collaborative "Co-pilot" experience for complex problem-solving (using AutoGen with Human-in-the-Loop).
Integrate with native cloud tools (like AWS/Azure Migrate, AWS MCP) to make data-driven, ground-truth recommendations.
2. The Intended Architectural Vision
The target architecture is a decoupled, microservice-based system designed for scalability, maintainability, and technological flexibility. It is built on four core pillars:
The Intake & Enrichment Service: The single point of entry for all external data. It uses unstructured.io for document parsing and LLMs for initial entity extraction, feeding the processed knowledge into the Knowledge Core.
The Knowledge Core (Universal Memory): The platform's brain, consisting of:
Vector Store (vector-service): For semantic search, using ChromaDB and a specialized model like jina-embeddings-v2-base-en.
Graph Store (graph-service): For dependency and relationship analysis, using Neo4j.
Object Store (storage-service): For raw files and artifacts, using MinIO.
The Agentic Orchestration Engine (ai-agent-service): The heart of the AI capabilities. It runs both CrewAI and AutoGen workflows, orchestrating other services by making API calls through its "Tools."
The API Gateway & Frontend:
backend: A pure, stateless API Gateway. Its only responsibility is to handle incoming requests from the frontend, perform authentication, and route them to the appropriate downstream microservice.
frontend: A modern React application that provides the user interface for all platform capabilities.
3. High-Level Component Structure
frontend/: The React-based user interface. It communicates exclusively with the backend API Gateway. api.ts is the key file defining this communication.
backend/: The FastAPI-based API Gateway. Its routers should contain the API endpoints, and its service_client.py should handle the HTTP calls to the other services.
services/: Contains all the specialized microservices. Each has its own main.py, routers, core logic, and Dockerfile.
project-service: Manages project and user metadata in PostgreSQL.
document-service: Converts raw documents to structured JSONL using unstructured.io.
vector-service: Manages embeddings and semantic search in ChromaDB.
graph-service: Manages the knowledge graph in Neo4j and performs entity extraction.
llm-service: A proxy and configuration manager for all external LLM API calls.
ai-agent-service: Orchestrates CrewAI and AutoGen workflows.
reporting-service: Converts final Markdown reports to PDF/DOCX.
storage-service: Manages file I/O with MinIO.
websocket-service: Handles all real-time communication with the frontend.
4. Intended Data Flow (Example: Document Processing)
Upload: Frontend -> Backend Gateway -> Storage Service (saves raw file).
Processing: Frontend -> Backend Gateway -> Document Service.
Enrichment: The Document Service produces a structured JSONL file and saves it to the Storage Service. It then orchestrates calls to:
The Vector Service to create embeddings from the JSONL.
The Graph Service to extract entities and update the graph from the JSONL.
Real-time Updates: Throughout this process, all services send status updates via the Websocket Service, which are displayed on the Frontend.
5. Current State of the Codebase (Known Issues)
The platform is in a transitional, hybrid state. A significant refactoring from a monolith to microservices has been started but is not complete. You should pay close attention to this.
The "Gateway + Monolith" Problem: The backend service is NOT a pure API Gateway. Its routers in backend/app/routers/ still contain direct imports and calls to old business logic in backend/app/core/. This old logic (e.g., rag_service.py, crew.py) directly accesses databases and performs heavy processing, completely bypassing the new, specialized microservices.
Redundant Logic: Because of the above, there are two parallel implementations for many core functions (e.g., entity extraction exists in both backend/app/core and services/graph-service).
Deployment Blockers: The code contains anti-patterns like sys.path manipulation for shared libraries, which must be fixed.
